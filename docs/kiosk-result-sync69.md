# 한정훈 전용 PWA 수동 조회 갱신

사용자가 UID69 한정 자동화와 PWA 수거기 조회 시 실행을 명시적으로 요청했다.
원본 서버에 원자적 갱신 계약이 확인되지 않아 기존 결과의 날짜 삭제 후 재등록을 사용한다.
이 동작은 같은 result_id의 업데이트가 아니며 성공할 때마다 결과 ID가 바뀐다.

## 실행 범위

- 로그인한 서버 사용자 ID와 조회의 사용자 ID가 모두69일 때만 실행한다.
- greenhug / VixVL4sPtmkwPaGHBWoR(여주아울렛06)의 유효한 실제 조회만 허용한다.
- 수동 조회 공통 경로에 연결한다. 10분 자동 측정/그래프 이력과 합치지 않는다.
- 진행 중인 근무/결과 제출 중에는 삭제·재등록하지 않고 기존 완료 제출 로직을 유지한다.
- 조회일과 같은 날짜에 기존 근무 결과가 정확히 한 건 있어야 한다.
  결과가 없거나 여러 건이면 사유만 표시하며 가짜 근무 결과를 생성하지 않는다.
- 기존 모든 결과 행, 실제 시작/종료, 근무/휴식시간, 업무/프로세스 버전을 보존하고 점검을 누적한다.
- 원본 JSON의 초 단위 시간·기기명·퍼센트·가용상태가 같은 점검 재생은 다시 쓰지 않는다.

## 실행 및 실패 처리

동일 origin의 브라우저 탭은 Web Locks로 순차 실행한다. 미지원 브라우저에서는 중단한다.
삭제 전에 복구 백업과 요청을 기기에 저장하고 읽어 대조한다. 저장 실패 시 삭제하지 않는다.
삭제 직전 재조회한 원본이 달라지면 중단한다(admin_name 표시 필드만 비교에서 제외).
삭제는 한 번, 비어 있음 확인 후 재등록도 한 번만 요청한다.
재조회로 단일 결과/반환 ID/전체 행/실제 시간과 필드를 대조한 뒤 성공 안내를 표시한다.

불확실한 삭제/등록/조회 실패 후 자동 재시도를 하지 않는다.
`kiosk_result_sync69_pending_v1`이 남아 있으면 이후 조회의 파괴적 동작을 차단한다.
`kiosk_result_sync69_last_backup_v1`에는 마지막 성공 전 원본과 요청을 보존한다.
장애 시 사이트 데이터 삭제/로그아웃/앱 재설치 전에 이 비공개 백업을 보존하고,
같은 사용자·날짜의 실제 서버 상태를 읽어 대조해야 한다. pending 키를 무작정 지우면 안 된다.
토큰·비밀번호는 백업이나 로그에 넣지 않는다.

## 한계와 검증의 구분

클라이언트 UID 제한은 서버 권한 검증을 대체하지 않는다. 로그인 세션의 Bearer 인증을 사용하며
401/403/CORS 실패를 무인증 요청이나 브라우저 보안 해제로 우회하지 않는다.
서버 트랜잭션이나 기기 간 공유 잠금이 없어 별도 기기의 동시 변경과 삭제 후 복원 실패 위험은 남는다.
실제 운영 결과1950의 단 한 번 삭제·재등록 성공과, 새 PWA 자동 경로 검증은 구분한다.
새 자동 경로의 HTTP 테스트는 모의 API이며 운영 로그인 세션에서 자동 갱신 성공을 증명하지 않는다.
근무 전/진행 중 결과가 없는 상태에서 원본 관리자 실시간 표시는 이 변경으로 지원하지 않는다.

## 1.24.4 완료 상태 차단 수정

실제 서버 읽기에서 결과1951/업무19행/1.4% 점검4개를 확인했으나,
이것만으로 완료 후 자동 갱신이 성공했다고 판단하지 않았다.
1.24.3의 WorkScreen은 서버에 제출된 뒤에도 pendingRecord를 보존하며,
새로고침 복구 시에도 완료 기록을 이 필드에 넣는다.
자동 갱신 가드가 pendingRecord 존재 자체를 전송 중으로 간주해 이 두 경로를 모두 차단했다.
원본 답변/기록 저장 동작은 유지하고 server_submitted가 true인 결과만 차단에서 제외했다.
미제출/응답 미확인/제출 중/진행 중 근무는 계속 제외한다.

새 Chromium 모의 API 시나리오는 근무 시작 → 정상 완료 → 수동 조회 →
재생 중복 방지 → 새로고침 완료 복구 → 다른 시각 조회의 흐름을 검사한다.
수정 전 라이브1.24.3에서는 완료 후 첫 조회 성공 안내를 기다리다 타임아웃으로 재현됐다.
운영 근무를 생성하거나 기존1951을 이 재현 테스트로 변경하지 않았다.
수정 후 로컬1.24.4에서 같은 시나리오가 통과했다. 완료 직후와 완료 복구 후 모두
점검을 누적하고, 기존 답변을 보존하며 같은 조회의 재생은 추가 요청하지 않았다.
Flutter 정적 검사와 릴리스 Web/PWA 준비도 성공했다.
재현 로그는 build/admin-sync69-before-fix.log, 수정 검증은 build/admin-sync69-after-fix.log다.
