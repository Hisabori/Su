# 접속 기록

접속 기록과 오류 진단을 분리합니다. 접속 기록은 비공개 Blob의 `access/v1/`에 저장하며, 오류 진단의 `suho_diagnostic` 중복 억제 규칙을 적용하지 않습니다. 사용자 ID 31만 수집하는 구조가 아닙니다. 31은 현재 설정된 **조회 관리자**이고 정상 인증된 모든 사용자 ID가 수집 대상입니다.

## 기록 시점

- `password_login`: Vercel 로그인 프록시가 기존 서버의 정상 로그인 응답에서 확인한 ID·이름으로 직접 기록합니다. 근무 조회가 실패하거나 기기가 배정되지 않아도 정상 로그인 응답은 기록합니다.
- `session_open`: 비밀번호·자동 로그인·패스키 방식으로 앱에 진입할 때 기존 서버의 토큰 검증 후 기록합니다. 앱이 30초 이상 백그라운드에 있다 복귀하면 별도 이벤트를 기록합니다.
- 비밀번호 로그인과 앱 진입은 다른 단계이므로 한 번의 로그인 과정에 두 종류의 기록이 생길 수 있습니다.
- 접속 시각은 서버가 정합니다. 클라이언트 시각이나 아이디 끝 숫자로 사용자 ID를 만들지 않습니다.
- 같은 이벤트의 재시도는 이벤트 ID를 유지합니다. 같은 서버 1분 구간에서는 같은 사용자·이벤트 ID의 저장 객체를 재사용하며, 서로 다른 사용자나 새 앱 진입은 묶지 않습니다.

기록 필드: 서버 사용자 ID, 서버가 확인한 이름, 서버 시각, 이벤트 종류, 클라이언트 유형, OS·브라우저 분류, 확인 번호, 인증 출처. 비밀번호·토큰·원본 User-Agent·IP 주소는 접속 기록에 저장하지 않습니다. OS·브라우저 분류는 기기 진단을 돕는 정보이며 인증 근거가 아닙니다.

## 사용자 식별

1. 비밀번호 로그인은 기존 서버의 정상 로그인 응답을 사용합니다.
2. 앱 진입은 토큰이 기존 서버에서 유효하다고 확인된 뒤 서버의 로그인 세션과 토큰 해시를 연결합니다. 커뮤니티 이용 시간이 지난 세션도 이 **쓰기 전용 접속 확인**에 사용할 수 있지만 만료된 커뮤니티·수거기·관리자 조회 권한을 복원하지 않습니다.
3. 세션 연결이 없으면 토큰 검증 응답의 명시적인 `user_id`를 사용합니다. 없을 때는 원래 서버가 해당 토큰을 유효하다고 확인한 경우에만 서명된 JWT의 명시적인 `user_id`/`userId`를 확인합니다. 클라이언트가 보내는 ID, 미검증 JWT, 아이디 끝 숫자, 의미가 불명확한 `id`/`sub`는 사용하지 않습니다.
4. 신뢰할 수 있는 ID를 확인할 수 없으면 `ACC-002`로 알립니다. 정상 업무 로그인은 유지하고, 업무를 마친 뒤 로그인 프록시를 통해 다시 로그인하면 연결할 수 있습니다.

## 조회

관리자 계정으로 커뮤니티를 연 뒤 상단 **접속 기록**에서 봅니다. 서버에서 최근 기록 100개씩 불러오며 ID·이름으로 **불러온 기록 안에서** 검색합니다. 숫자 검색은 서버 ID와 정확하게 일치시키므로 31을 검색할 때 310이 섞이지 않습니다. 이전 기록은 추가로 불러올 수 있습니다.

일반 사용자가 접속 기록 API를 직접 호출해도 목록을 읽을 수 없습니다. 서버는 현재 관리자 설정과 인증을 확인합니다. 수집은 관리자 여부와 관계없이 수행합니다.

## 오류 코드

| 코드 | 의미 |
|---|---|
| ACC-000 | 접속 기록 저장 성공 |
| ACC-001 | 토큰·접속 조회 세션 인증 필요 또는 만료 |
| ACC-002 | 서버에서 확인 가능한 사용자 연결이 없어 다시 로그인 필요 |
| ACC-003 | 잘못된 요청·이벤트 ID·페이지 위치 |
| ACC-101 | 원래 서버의 인증 확인 또는 세션 저장소 읽기 실패 |
| ACC-201 | 접속 기록 목록 조회 실패 |
| ACC-202 | 접속 기록 저장 실패·저장 미확인 |
| ACC-203 | 클라이언트와 접속 기록 서버의 연결 지연·시간 초과 |
| ACC-204 | 클라이언트가 받은 응답 형식 오류 |
| ACC-403 | 관리자 조회 권한 또는 허용된 주소 확인 실패 |

저장 실패가 정상 로그인 성공을 뒤집지는 않습니다. 앱 접속 기록은 재시도하고 실패하면 오류를 알리며, 설정의 **접속 기록**에서 저장 상태와 재시도 버튼을 제공합니다. Vercel Runtime Logs의 `access_record`는 서버에서 확인한 사용자 ID·이벤트 종류·저장 여부·오류 코드를 표시합니다. 비공개 Blob에 저장되지 못한 경우에는 `stored:false`로 표시하며 저장됐다고 보고하지 않습니다.

## 범위

이 저장소의 최신 앱·웹과 Vercel 로그인 프록시에서 수집합니다. 프록시를 거치지 않는 변경 전 APK나 다른 외부 앱의 모든 접속을 원래 서버 권한 없이 자동 수집하는 기능은 아닙니다. 클라이언트나 네트워크가 완전히 끊긴 상태의 접속은 실시간 서버 기록을 보장할 수 없습니다. 인증 근거가 부족한 기존 세션은 경고를 확인하고 다시 로그인해야 합니다.
